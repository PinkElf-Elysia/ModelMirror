## 完成结果

你会发布一个由 ModelMirror 只读检查的邮件工作流。首次启用只记录 INBOX 当前最高 UID；之后每封新邮件各启动一次执行，不会标记已读、移动或删除邮件。

## 适用对象

适合处理公告收件箱、需求登记、系统通知或人工审核来信。首版只支持公网 IMAPS 993、固定 INBOX、用户名与应用密码；OAuth2、IMAP IDLE、多文件夹、附件内容和原始 HTML 不在范围内。

## 开始前

向邮箱服务商申请应用密码，不要使用账户主密码。请管理员开启 `WORKFLOW_IMAP_TRIGGERS_ENABLED`；开关关闭时可以编辑和静态发布，但不能检查邮箱、手动测试或启用订阅。

邮件用户名和应用密码会作为 generic 凭据加密保存，工作流定义只保留凭据 ID。轮换同一个凭据会立即生效，撤销后下一次检查会安全失败。

## 真实范例

团队用一个专用收件箱接收产品反馈。新邮件到达后，工作流先按主题和安全纯文本做条件判断，再把需要复核的内容交给 Agent 分类，最后写入数据表。附件只记录数量，内容不会被打开。

## 操作步骤

1. 在[经典工作流画布](/workflow)添加“邮件到达入口”。
2. 填写 IMAP 公网域名，例如 `imap.example.com`。不要加入 `imaps://`、端口、IP 地址或变量。
3. 选择已有 generic 凭据，或在节点中输入凭据名称、邮箱用户名和应用密码后加密保存。
4. 选择“检查邮箱”，确认 INBOX 可只读访问，并核对当前邮件数和最多三封摘要。该操作不改变已读状态。
5. 设置检查频率，并配置事件元数据、邮件元数据和安全纯文本三个运行变量。
6. 连接条件、内容策略、Agent 或数据表节点。邮件是外部不可信输入；连接模型或 HTTP 时，正文可能被发送给对应服务。
7. 手动测试会读取当前最新一封邮件并真实执行下游节点，但不会创建订阅或移动 UID 基线。
8. 发布并启用版本。打开顶部紧凑的“邮件订阅”状态入口，确认“监听中”，并查看下次检查、最后成功时间和连续失败次数。

## 常见问题

### 为什么启用后没有处理已有邮件？

首次成功检查只建立当前 `UIDVALIDITY` 和最高 UID 基线，避免把历史收件箱误当作新事件。只有之后出现的新 UID 才会启动执行。

### 邮件会被标记为已读吗？

不会。运行器使用只读 INBOX 和 `BODY.PEEK[]`。它不会写 `Seen`、移动、删除或发送邮件。

### HTML 邮件和附件如何处理？

若存在 inline 纯文本则优先使用；HTML-only 邮件会移除脚本、样式、表单和嵌入内容后转换成纯文本。附件只统计数量，不解码、不保存，也不会把文件名写入工作流变量。

### 服务重启会重复执行吗？

已经物化的邮件执行只保存 UID、UIDVALIDITY 和哈希。服务重启后会按 UID 重新只读获取邮件，并复用原执行；不会创建第二条执行。若邮件已经被外部删除，该执行会安全失败。

## 限制

每轮最多处理 100 个新 UID；单封原始邮件最多 1 MiB，规范化正文最多 256 KiB，最多 100 个 MIME part、20 层嵌套和 50 个收件地址。邮件工作流不能包含定时入口、挂起等待、人工介入、MCP 工具或等待结果的 Agent 移交。

主题、地址和正文只存在于当前执行内存，不写入部署 Store、SSE、checkpoint、执行摘要或失败事件。正文变量固定带“不可信外部邮件”边界，但这不等于能够识别语义越狱或提示注入；需要模型前策略时请显式加入内容策略中间件。

首版是单实例文件 Store，不宣称多 Worker 或 HA。IMAP 服务商的可用性不由 ModelMirror 保证；先用专用测试邮箱和无副作用下游完成灰度，再接入正式收件箱。

## 下一步
