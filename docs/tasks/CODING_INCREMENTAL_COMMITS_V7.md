# 任务卡：CODING-INCREMENTAL-COMMITS-V7

> 第七轮把单次 Coding 草稿扩展为最多十轮的线性本地修改历史。本任务风险等级为
> L4；出现部分写入、重复提交、旧轮覆盖、累计 Patch 越界或恢复结果不确定时必须停止。

## 1. 目标与基线

- 基线：PR #77 合并提交 `4863c8becca098c72f6195d96ac96272909cc61b`。
- 分支：`codex/coding-incremental-commits-v7`。
- 工作树：`C:\tmp\modelmirror-coding-v7`。
- 同一任务最多开始 10 轮“修改、验证、应用、本地提交”；每轮形成一个线性提交。
- 页面默认审阅本轮变化，同时保留历史并可下载累计 Diff。
- 仅允许撤销最新一轮；更早轮次不得被页面或 Agent 改写。

本轮不包含远程仓库、push、PR、分支选择、merge/rebase、Agent Shell/Git、多 Agent、
完整 ACP、分布式 Worker或生产级多租户。

## 2. 不可变边界

- 真实主工作树和实现工作树不作为写入目标；只能操作预先配置的独立本地仓库。
- Agent 和浏览器不能提交路径、命令、分支或 Git 参数；Runtime 仍不能使用 Shell/Git。
- 累计最多 20 个文件、单文件 512 KiB、累计最终 Patch 1 MiB；历史增量 Patch 合计
  最多 10 MiB。轮次编号只增不减，已撤销轮次仍计入 10 轮上限。
- 项目验证针对不可变源码加全部已保留轮次和当前草稿后的累计状态。
- Applier 必须确认目标精确匹配上一检查点，只写本轮增量；Committer 必须以当前
  固定分支 HEAD 为父提交并原子更新引用。
- 只可撤销最新提交；撤销提交保留文件，随后才允许撤销该轮应用。存在后续草稿时
  必须先放弃草稿。
- 恢复继续不保存对话；外部状态不明确时进入只读冲突态，不重复应用或提交。

## 3. 公共行为

- `capabilities` 公开 incremental 可用性、10 轮上限、恢复依赖和 latest-only 撤销策略。
- 会话新增历史查询和“继续修改”；现有 Patch 下载增加本轮与累计两个安全范围。
- 提交成功后保持会话可查看，用户明确选择“继续修改”才建立下一检查点。
- `CODING_INCREMENTAL_ENABLED=false` 时保留第六轮单次流程；Recovery、Applier 或
  Committer 缺失时不得静默启用多轮流程。
- 所有响应继续 `no-store`，不返回绝对路径、文件正文、原始协议、密钥或操作日志。

## 5. 验收与停止条件

- 使用随机文件名完成纯文档、后端、前端和同文件再次修改，确认本轮 Diff、累计 Diff
  和 Git 父子关系准确。
- 在草稿、验证、应用、提交和回执落盘窗口分别重启，确认不重复写入或提交。
- 撤销最新轮只恢复上一检查点；旧轮撤销、外部文件/索引/分支变化均失败关闭。
- 达到第 10 轮后仍可查看、下载和结束任务，但不能继续。
- v1 恢复记录兼容读取；密钥错误、密文损坏和基准不一致不得被覆盖或继续写入。
- 任一专项或全量回归失败、前端侵入 ChatPage、引入依赖、泄露敏感信息或无法独立
  回退时不得进入人工验收。

## 6. 回退与交付门禁

- 删除恢复记录不修改独立仓库；目标冲突时由开发者重建专用仓库。
- 完成七个本地提交和自动门禁后停止；用户重建容器并明确验收通过前不推送、不创建 PR。

## 8. 人工验收暴露的问题与新增护栏

本轮在 Windows Docker Desktop 绑定目录上完成三轮真实修改、验证、应用、提交和重启恢复后，补充以下 Harness 约束：

1. **全量内容哈希不得位于交互请求热路径。** 约 570 个文件的单次全量读取耗时实测约 36 秒，多次扫描会造成写入或提交已经成功但 Server 先超时。不可变基准仍在启动时全量校验；运行时遍历全部路径和元数据，只重新哈希发生变化的文件。
2. **超时不等于操作失败。** Applier 与 Committer 使用不透明操作 ID 和幂等对账。连接中断、超时或回执丢失后必须先查询或 reconcile，确认外部状态后才能重试、撤销或清理，禁止直接重复写入和重复提交。
3. **确认窗口必须覆盖实际平台波动。** Windows 实测单文件应用约 21–28 秒、本地提交约 33 秒；Applier 与 Committer 确认窗口统一为 90 秒。扩大窗口不能替代性能修复，交付前必须记录真实计时。
4. **容器 healthy 不代表执行面可用。** 人工验收和重建门禁必须从 Server 经共享 Unix socket 调用 Runtime、Verifier、Applier 和 Committer 的私有 health；socket 缺失、路径错误或不可连接时视为不可用。
5. **增量恢复允许当前轮为空。** 已完成轮次保存在 `base_patch/base_paths`，刚提交并继续时当前 `patch/paths` 可以同时为空。两组字段分别要求成对，不能用“当前路径必须非空”的单轮假设拒绝合法恢复。
6. **重建前先判断恢复指纹影响。** 完整镜像重建会改变不可变源码指纹，旧恢复记录应过期而不是被强行继续。若必须验证同一份待恢复数据，只能使用保持源码快照层不变的受控临时镜像层；验收后仍需回到可复现的完整构建。
7. **Windows 专用仓库统一使用 LF。** 实现副本和提交目标以 `core.autocrlf=false` 创建并在重建前比较净化指纹，避免内容一致但换行不同导致 `target_not_ready`。
8. **修复请求不能提前清空完整状态。** 用户从失败结果发起下一轮修复时，前端必须保留上一轮回答、计划和失败摘要，直到服务端确认新一轮已经开始；请求拒绝、网络延迟或模型不可用时，最后一份完整状态继续可见。

新增停止条件：任何操作超过确认窗口、出现成功状态与页面结果不一致、容器健康但私有 socket 不可达，或恢复记录只有累计 Patch 而无法继续时，必须保留现场并先完成日志、目标仓库和恢复记录三方对账。
