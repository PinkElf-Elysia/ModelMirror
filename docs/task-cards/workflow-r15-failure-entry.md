# 工作流 R1.5 PR1：失败处置入口

## 目标

在独立工作流发布运行面增加自研 `failure_event_entry`，让一个已发布工作流可以订阅 1–50 个来源项目的后续失败，并以脱敏事件启动处置链。该节点不进入 Xpert 内嵌工作流，也不开放远程触发接口。

## 固定边界

- 只处理独立发布运行面的触发执行；浏览器草稿运行和激活前历史失败不派发。
- 一个来源项目同时最多绑定一个已激活处理器；自订阅、重复来源、缺失来源和订阅冲突均拒绝。
- 失败事件只包含项目、固定版本、部署/执行/任务/运行 ID、触发类型、失败时间、脱敏错误摘要和可确定的失败节点信息。
- 请求正文、变量快照、凭据、Cookie、认证头和堆栈不持久化、不进入事件。
- 失败处置执行带 `suppress_failure_dispatch=true`，其自身失败不会递归派发。
- 本批不提供自动重试、补偿、历史回放或全局兜底。

## 开关与灰度

`WORKFLOW_FAILURE_TRIGGERS_ENABLED=false` 为默认值。关闭时允许编辑和发布，但激活失败入口返回 409，协调器也不会运行待处理失败事件。

灰度顺序：

1. 配置并发布内部失败处理工作流，保持未激活。
2. 打开环境开关并重启单实例服务。
3. 激活一个内部处理器，制造一次无敏感数据的测试失败。
4. 核对来源、固定版本、唯一 occurrence key、脱敏摘要和一次性执行。
5. 再逐步增加来源项目。

## 持久化与恢复

Store 文件升级为 additive `workflow-deployments-v2`，新增顶层 `failure_subscriptions`。旧 v1 文件缺少该表时自动按空表加载。来源失败状态与处理器执行在同一次原子替换中写入，唯一键为：

```text
failure:{source_execution_id}:{handler_deployment_id}
```

运行中失败处理器会在执行期间续租；状态提交必须携带领取时的 lease token，失去租约的旧 Worker 不能覆盖新 Worker 的状态。单实例重启后，过期租约恢复为待处理并重新领取；重复失败回调不会创建第二个处理器执行。v2 加载会拒绝重复、悬空、非激活或类型不匹配的失败订阅，不以“取最后一条”掩盖损坏快照。

唯一性边界是“一个 occurrence 对应一个持久执行记录”。如果进程在外部副作用已经发生、但终态尚未落盘的瞬间崩溃，同一执行记录可能在租约过期后恢复运行；R1.5 不宣称跨外部系统的 exactly-once。失败处理链中的外部写操作仍应携带业务幂等键。

## 验收

- NodeContract、前后端节点类型、Registry、Palette 和变量目录一致。
- Planner 默认关闭，Xpert/evaluation/app 入口拒绝该节点。
- 发布校验合法/非法来源，激活校验开关和订阅冲突。
- 失败派发原子、幂等、可恢复、脱敏且不递归。
- 错误摘要覆盖 Header、JSON、查询参数、URL userinfo 和常见令牌格式；失败节点 ID/标题使用同一脱敏边界。
- 服务端或旧草稿缺少 React Flow 位置、或保存的是语义节点 type 时，前端水合为安全位置和 `workflowNode`，不得白屏。
- 停用只阻止新事件，不取消已经物化的处理器执行。
- `GET /api/workflows` 只返回安全项目摘要，并支持分页、激活状态和触发类型过滤。

## 回退

先把 `WORKFLOW_FAILURE_TRIGGERS_ENABLED` 设为 `false`，再停用所有失败处理器，然后回滚代码。不要删除 `workflow_deployments.json`；R1 定时、Webhook、挂起等待和旧执行摘要仍可继续使用 v2 中的原有表。
