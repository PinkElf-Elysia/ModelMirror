# M2 补充批次：摘要溢出后二次压缩

本目录是本补充批次的当前记录；原 rolling-summary 文档、既有 PR 和真实验收记录作为历史保留，不改写。用户已批准以下新增调用边界。本交付已完成离线/UI验证、一次真实压缩及追加素材后的再次真实压缩；用户接受已知偏差作为初版边界。

## 冻结行为

- 仅对完整返回（finishReason=stop）、超过 10000 个 Unicode 字符的滚动摘要触发一次额外压缩。使用 Array.from(text).length；10000 不触发，10001 触发。截断输出不进入压缩。
- 使用当时明确选定的摘要模型及其已批准参数，独立冻结的压缩指令；目标约 2000 字，结果非空、完整且最多 3000 字符才可发布。剧情模型和作者原文不变。
- 压缩输入只有超长摘要正文及独立压缩指令，不重新附加原历史，不混入工程回执。滚动摘要的来源仍是前一有效摘要及未覆盖的完整历史。
- 超长候选不会先成为有效摘要。两次完整原文、请求 hash、响应 hash 和回执分别保留；压缩成功后才发布原覆盖范围的新版本。下一次滚动使用压缩后的有效正文。
- 空输出、截断、超限、网络失败、撤权或取消均不会引发自动补写、换模型或循环压缩。旧有效摘要和完整原始历史保留。人工编辑超过 10000 字符仍直接拒绝，不新增自动调用。
- 输入本身超过控制面容量时仍按原合同拒绝并暂停。本批不是自动切块、检索或输入 token 溢出的通用解决方案。

## 额度与恢复

| 操作 | 最大原子预留 | 正常派发 |
| --- | --- | --- |
| 发送前需要新摘要 | 3 | 摘要、按需压缩、剧情 |
| 单独更新或后台更新 | 2 | 摘要、按需压缩 |
| 摘要已覆盖，只生成剧情 | 1 | 剧情 |
| 已确认压缩失败后的明确再次压缩 | 1 | 条件一致时复用原超长候选 |

预留不足时不会先派发部分调用。未派发的预留释放；已派发、失败、取消和未知继续计数。这里描述服务端额度，不代替供应商账单审计。

再次压缩须由玩家明确操作；仅在来源、前一摘要版本、覆盖范围和摘要模型绑定仍一致时复用候选。未知结果必须先核对原操作，不能换 ID 重放。重启恢复只收束已有回执，绝不启动尚未派发的压缩或剧情。摘要成功但剧情未执行时，保留摘要并由玩家后续主动发送。
