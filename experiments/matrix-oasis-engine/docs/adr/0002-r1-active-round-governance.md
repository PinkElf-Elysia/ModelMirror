# ADR-0002：采用活动轮次策略并冻结 Creator

- 状态：已接受（R1.1）
- 日期：2026-08-07

## 背景

R0 策略把基线、工具和产物限制直接命名为 R0。R1 需要在保留隔离强度的同时，只允许合同与验证器演进，并保证 R0 Creator 不被顺手修改。

## 决策

- `module-boundary.json` 升为 schema v2，固定 `activeRound=R1` 与活动轮次基线。
- 工具和产物策略使用轮次无关键名，避免未来通过改名弱化护栏。
- 父仓范围检查拒绝模块外变更；R1 范围检查同时拒绝 `apps/creator-web/**` 变更。
- R1 范围检查纳入 `verify`。在历史拆分后的 standalone 仓中仅返回明确的 `not_applicable`；其他位置或 Git 错误失败关闭。
- 父项目交互继续为 `none`，Godot、插件、二进制、网络与模块外依赖限制不变。

## 结果

- R1 可以独立演进合同与验证器，同时机器化证明 Creator 和父仓零改动。
- R0 Creator 页面继续作为历史快照，不能宣称反映 R1 能力。
- 每轮仍需刷新并固定新基线；基线变化不能由命令行调用者绕过。

## 被拒绝方案

- 沿用 R0 基线检查：会把已合并历史与 R1 差异混在一起。
- 只靠人工审查 Creator：不能在并行工作树中失败关闭。
- 在根 CI 注册模块：需要修改父仓共享配置，超出 R1 边界。
